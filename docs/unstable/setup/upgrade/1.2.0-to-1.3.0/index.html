    Migrating from v1.2.0 to v1.3.0¶

    Table of Contents¶

    • New Features
    • Requirements

    • Upgrade Steps

    New Features¶

    Katana Blade render engine¶

    Views are now rendered with Katana, a standalone implementation of the Blade templating language. This brings real template inheritance, reusable <x-...> components, shared partials and the full set of Blade directives (@if, @foreach, @forelse, @include, and more) to your views. See the rewritten Views documentation for what is now possible.

    UUIDs on authentication objects¶

    Users, roles, groups, organizations, sessions and api keys (and the z_file table) carry a UUID next to their numeric ID. It is the identifier meant to leave the application - URLs, REST payloads, anything handed to a third party - because it does not reveal how many records exist and cannot be guessed by counting up. The numeric ID stays the internal key.

    Every object that can be retrieved by ID can also be retrieved by UUID, and every object exposes its own:

    $user = User::byUuid($uuid);
$roles = Role::byUuids(...$uuids);

user()->uuid;
$user->uuid();
$organization->uuid();

    For a session or an api key the UUID is the only identifier safe to publish - the token authenticates whoever presents it, so it belongs in a cookie or an Authorization header and nowhere else. Use the UUID to address a session in a "your active sessions" list:

    $session = Session::byUuid($uuid); // scoped like byId(): never returns an api key
$key = APIKey::byUuid($uuid);

    See Access Control for the full API.

    Organization self-management¶

    Members can manage their own organization in the Z-Admin panel at /z/organization: rename it (z.organization.rename), invite existing accounts by link (z.organization.invite) and hand out roles that are released to organizations (z.organization.roles). The sidebar entry and the dashboard card show up with z.organization.manage. A role is released with the new Organizations may assign this role to their members checkbox on its page under Roles. Nothing is released after the upgrade, so organizations can only hand out roles once you tick it.

    See Organization Management.

    Two factor authentication¶

    Accounts can protect their logins with a time based one time password from an authenticator app. Users set it up on their profile page. A login of an account with two factor then asks for the code in a modal before the session starts, and $req->requireFreshTwoFactor() guards a single action behind a check within two_factor_freshness_seconds (defaults to 900).

    The modal ships with <x-zubzet::body/>. A layout that leaves out the body essentials cannot finish a two factor login until it renders <x-zubzet::authentication.two-factor/> itself.

    See Two Factor Authentication.

    Profile page¶

    Every logged in account has a profile page at /z/profile: password change, two factor, sessions and api keys. It is built from the zubzet::account.* components, which can be placed on any page. See Profile.

    A password change ends every login of the account but no longer its api keys, and neither does $user->clearSessions(). Revoke keys through APIKey::byUser() where a password change used to end them.

    Requirements¶

    MariaDB 11.7 or newer¶

    v1.3.0 raises the minimum database server to MariaDB 11.7. Older servers are no longer supported.

    ZubZet targets MariaDB, not MySQL: the framework-bundled migrations use MariaDB-only syntax (ALTER TABLE ... ADD COLUMN IF NOT EXISTS), which MySQL rejects. The development stack and the e2e suite run MariaDB 11.8.

    Check what your server runs:

    SELECT VERSION();

    Breaking Changes¶

    Views are now Blade templates¶

    The old view format, a PHP file returning head and body closures, has been replaced by Blade .blade.php templates. The change is mechanical and the migrator applies it for you:

    • A view's body closure becomes @section("content").
    • A view's head closure becomes @section("head").
    • Every view starts with @extends($layout), so the view plugs into the layout the controller chose.
    • Layouts drop their $body($opt) / $head($opt) calls in favor of @yield("content") / @yield("head"), and the framework essentials become the <x-zubzet::head :opt="$opt"/> and <x-zubzet::body :opt="$opt"/> components.

    Before:

    <?php return ["body" => function($opt) { ?>
    <h1><?= $opt["title"] ?></h1>
<?php }]; ?>

    After:

    @extends($layout)

@section("content")
    <h1>{{ $opt["title"] }}</h1>
@endsection

    Plain PHP still works inside a .blade.php file, so raw <?php ?> blocks in your views keep running unchanged. See the Views documentation for the full picture.

    Upgrade Steps¶

    Follow these steps to upgrade your project to v1.3.0.

    1. Upgrade the database server first¶

    Bring the server to 11.7 or newer before applying the migrations of this release. With the Docker stack, bump the mariadb image in packaging/docker/docker-compose-base.yml and recreate the container:

    image: mariadb:11.8

    2. Automated migration (recommended)¶

    The ZubZet Version Migrator converts every view and layout in your project automatically.

    1. Clone the tool: zubzet/version-migration
    2. Preview the changes with a dry run, then apply them:
    php application.php upgrade {PATH_TO_YOUR_PROJECT} 1.2.0 1.3.0 --dry
php application.php upgrade {PATH_TO_YOUR_PROJECT} 1.2.0 1.3.0

    The migrator bumps the framework dependency and rewrites every return [...] view and layout to Blade (.blade.php), including the section, @extends and essentials-component changes above. It also adds the CSRF field to raw post forms (see step 7) and removes app-local copies of Z.js, which predate the CSRF header, and adds a .htaccess to webroot/uploads/ (see step 12). Review each prompted change before accepting it.

    3. Review your migrated views¶

    The conversion is output preserving, but it is worth skimming the result. Views that already used raw <?php ?> keep it verbatim, and anything the framework could not classify is left as raw PHP rather than guessed at. Once you are comfortable with Blade, you can gradually adopt directives like @foreach or components where they make a template clearer. The Views documentation covers what is available.

    4. Apply the database migrations¶

    The framework-bundled migrations are applied by the project's normal start/seed flow (npm run start, which runs db:seed → migrations then seed) or directly with:

    docker exec application php index.php db:migrate

    New since v1.2.0:

    Migration Change
    2026-09-02_user_locale_bcp_47.sql Adds the nullable z_user.locale_bcp_47, the user's preferred locale.
    2026-09-07_session-api-key.sql Adds z_logintoken.name, is_permanent and is_apikey.
    2026-09-08_session-device-and-ip.sql Adds z_logintoken.device, reason, ip_creation and ip_last.
    2026-09-08_uuid.sql Adds the NOT NULL, unique uuid column (native UUID type) to z_user, z_role, z_organization, z_logintoken and z_file.
    2026-09-09_session-expires-at.sql Adds the nullable z_logintoken.expires_at (TIMESTAMP), the fixed expiry that overrides the computed session lifetime.
    2026-09-17_session-last-used-and-token-index.sql Adds the nullable z_logintoken.last_used (TIMESTAMP).
    2026-09-21_two-factor-challenge.sql Creates z_two_factor_challenge for the login's two factor step, and adds z_logintoken.last_two_factor, z_user.two_factor_secret and z_user.two_factor_confirmed_at.
    2026-09-21_2_session-two-factor-tries.sql Adds z_logintoken.remaining_two_factor_tries (defaults to 5).
    2026-09-23_group-org-assignable.sql Adds z_role.is_org_assignable (TINYINT(1), default 0), which releases a role or group to organizations.

    If you manage schema by hand, the equivalent statements are idempotent (... IF NOT EXISTS).

    5. Check code that builds URLs from the root directory¶

    v1.3.0 fixes how a non-empty rootDirectory is handled. With an empty rootDirectory (the default, and what the Docker stack sets through CONFIG_ROOTDIRECTORY: "") nothing changes. Below a root directory such as sub:

    Value v1.2.0 v1.3.0
    $opt["root"], $req->getRootFolder(), Z.Request.rootPath /sub /sub/
    $opt["absRoot"], $opt["application_root"], $req->getRoot(), config("root"), Z.Request.absRoot, Z.Request.rootHost https://example.com/sub https://example.com/sub/
    Route::get("/hello") on /sub/hello no match (compared against the full path) matches
    getUrlParts() of /sub/a/b with rootDirectory = sub/ ["b"] (the slash counted as a segment) ["a", "b"]
    $res->reroute(["a", "b"]) 404 (the root directory was missing from the rerouted path) runs a/b

    The only code that needs a change is code that adds its own slash after the root. The router answers the resulting /sub//login like /sub/login, so such links keep working until cleaned up:

    // before: /sub//login after the upgrade
$opt["root"] . "/login"
// after
$opt["root"] . "login"

    Search your project for a slash right after any of the values in the first two rows (root"] . "/, root ?>/, {{ $opt["root"] }}/, rootPath + "/", ...) and for paths with a leading slash handed to helpers that prepend the root themselves (rerouteUrl("/, Z.Request.root("/). Routes, reroute() calls and getUrlParts() need no change as long as they are written relative to the root directory, which is the only form that worked before.

    A cookie path taken from getRootFolder() now ends with a slash as well, so the browser no longer sends that cookie on the bare /sub. Pass rtrim($req->getRootFolder(), "/") ?: "/" instead, as the framework does for its maintenance cookie.

    What was checked¶

    Before the release, the change was checked against eleven existing applications, built on framework versions from v0.11 to v1.3.0-alpha, by reading their code against the old and the new behaviour. Each application was checked for:

    • every concatenation of $opt["root"], $opt["absRoot"], getRoot(), getRootFolder(), config("root") and Z.Request.rootPath/rootHost/absRoot in controllers, models, views, mail views and JavaScript
    • Route:: definitions and groups, reroute(), rerouteUrl(), getUrlParts() and direct REQUEST_URI access
    • .htaccess (RewriteBase), maintenance and login cookie paths, and debug bar usage
    • overrides of email_password_reset and translation keys under email.*
    • the effective rootDirectory per environment: the INI value, the Docker setup and the production and staging deployments

    Result:

    Setup found Applications Outcome
    Deployed with CONFIG_ROOTDIRECTORY: "" (every production, staging and Docker environment) 11 Identical values, routes and reroutes
    INI rootDirectory without a trailing slash (sub, also with spaces) 5 Links like /sublogin and routes below the root are fixed
    INI rootDirectory with a trailing slash (sub/) on v1.2 2 The autorouter no longer strips the controller, links are fixed
    INI rootDirectory with a trailing slash (sub/) on v0.11 to v1.0 2 Identical values, those versions already used the value verbatim
    INI rootDirectory empty 2 Identical values
    A slash added after the root (root . "/path") 0 Would keep working with a doubled slash, the change shown above removes it
    Route:: paths that include the root directory 0 Would need the root directory removed

    Root directories with spaces (My App) behave the same: the router decodes the request path before stripping the root directory, and getUrlParts() counts the encoded segment as one, so both agree on real requests and on reroutes.

    The e2e suite serves the application below /sub as well and covers this in tests/cypress/e2e/core/root-directory.cy.js (links, assets and the debug bar, Route:: definitions, reroutes, a doubled slash after the root, the maintenance cookie, the password reset mail) and tests/cypress/e2e/core/request.cy.js (getUrlParts() with one, two and slash-wrapped segments, and a doubled slash after them).

    6. Send the login warning yourself if you relied on it¶

    Too many failed logins no longer send the "Security alert" email to the account owner; the login is still blocked and logged as ACCOUNT_LOGIN_RATE_LIMITED. The email_too_many_logins view, the z_login_too_many_tries table and the z_loginModel helpers around it stay, so no migration is needed, but the framework no longer calls them. To keep the warning, send it when checkLoginTries() returns false:

    if(!$user->checkLoginTries()) {
    $res->sendEmailToUser($user->id(), "Security alert", "email_too_many_logins.php", [
        "date" => date("Y-m-d H:i:s"),
        "ip" => $req->ip(),
    ]);
}

    $req->ip() prefers the HTTP_CLIENT_IP and X-Forwarded-For headers, which the client controls, and the view prints it unescaped. Validate it with filter_var($ip, FILTER_VALIDATE_IP) before it goes into the mail, otherwise an attacker can put HTML into a security mail to the account owner. checkLoginTries() returns false on every blocked attempt, so the example sends one mail per attempt. Throttle it, the removed code sent at most one mail per 10 minutes.

    7. Check forms and scripts that post to the framework¶

    Every request other than GET, HEAD and OPTIONS that a browser could send cross-site now has to return the z_csrf cookie as an X-CSRF-Token header or a _csrf form field, otherwise it is answered with 403 and csrf token mismatch. Z.Forms and Z.Request attach the header themselves. Look for everything else:

    • A raw <form method="post"> has to embed the token. The migrator adds it to the forms in your views, check the ones it reports and forms built elsewhere:
    <form method="post">
    {!! \ZubZet\Framework\Security\CSRF::field() !!}
    • A custom form-encoded fetch() or $.ajax() post has to send Z.Request.csrfToken() as the X-CSRF-Token header.
    • An endpoint that authenticates without the session cookie (form-encoded API keys, navigator.sendBeacon()) needs ->withoutCsrf() on its route or group.
    • Requests with a Content-Type other than a form one, like JSON, and requests with an Authorization header other than Basic, Digest, NTLM or Negotiate are not checked.
    • The login runs only for a post with action=login now. A custom login form or script that posts just name and password is answered with the login page, so it has to send the field.
    • The bundled forgot password page redirects to /login after the request, without the "email sent" alert.

    See CSRF Protection.

    8. Check what depends on the session cookie¶

    The z_login_token session cookie and the maintenance bypass cookie now carry SameSite=Lax, and Secure whenever the host setting starts with https://. This can break three things:

    • A deployment whose host says https:// but is served over plain HTTP loses its logins until host matches the real scheme.
    • A cross-site POST that returns to the application (OIDC form_post, SAML, payment returns) arrives without the session cookie.
    • A request from a cross-site iframe has no session cookie either, and z_csrf is not stored there, so every post from it ends in 403.

    9. Post to z/login_as/{id}¶

    The Z-Admin panel's z/login_as/{id} answers only a post with action=login_as and the CSRF token, with an optional reason. It returns {"result": "success"} instead of redirecting, and a GET is answered with 405, because a link on another site could otherwise switch an admin to another user. The Login as button on the user page already posts it. A link or script of your own that opens z/login_as/{id} has to post instead.

    10. Set encryption_key if you use secrets¶

    encryptSecret() and decryptSecret() need the encryption_key setting, at least 32 bytes. Set it via CONFIG_ENCRYPTION_KEY and keep an empty encryption_key = line in z_settings.ini, because environment variables only override settings that exist there. Values encrypted with a key cannot be recovered once it is changed or lost.

    See Secrets.

    11. If requests fail with "Illegal mix of collations"¶

    Framework tables are now created as utf8mb4 / utf8mb4_uca1400_ai_ci. Existing installations are not converted, because converting rewrites every table. If tables created under different server defaults make queries fail with Illegal mix of collations, convert the framework tables once, ideally in a maintenance window:

    docker exec application php index.php repair:database-collation

    Add --include-app-tables to convert the application tables too and to set the database default.

    See Console Commands.

    12. Protect other upload folders in the webroot¶

    Files in webroot/uploads/ are only served now, never run through PHP: the migrator adds a .htaccess there. Without it, an upload field that accepts the php extension lets anyone run code by opening the uploaded file. If uploadFolder or an upload() call points to another folder in the webroot, put the same .htaccess there:

    <Files "*">
    SetHandler None
</Files>
